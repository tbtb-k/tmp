PART 1

全体像

今回の進め方と、ソリューションによる移管の基本概念

  • ここでは「なぜソリューションという入れ物が必要なのか」を腹落ちさせる。
SCENARIO

今回の進め方 — 新環境の完成を待たずに先行開発する

STEP 1

既存環境で開発

新環境の準備と並行して、いま使える環境でエージェントを作り込む。

STEP 2

ソリューションに梱包

エージェントと依存コンポーネントを1つのソリューションにまとめ、エクスポート。

STEP 3

新環境を整える

Dataverse・ロール・ライセンス／容量を揃え、受け入れ可能な状態にする。

STEP 4

インポート＆公開

取り込んだあと、接続・環境変数・認証を再設定し、公開してチャネルへ。

先に共有しておきたい注意点新環境にライセンス／容量が割り当たっていない段階では、取り込みや編集まで進めても「公開」まで到達できない可能性がある。移行作業とライセンス手配は並行して進めるのが安全（詳細は PART 4）。
用語ミニ解説環境：Copilot Studio やアプリを置いておく「部屋」のこと。開発用・本番用のように用途で分けて使うテナント：会社ごとに割り当てられた Microsoft 365 の領域。今回は同じ会社の中での部屋の引っ越しライセンス／容量：エージェントを実際に使うために必要な利用権。これが無いと作れても「公開」できない
  • この進め方自体は推奨できる。開発待ち時間を作らずに済む。
  • ただし STEP 3 を後回しにすると、当日「公開できない」で止まる。ここだけ先に握っておきたい。
CONCEPT

基本概念：ソリューションという「運搬用の箱」

WHAT

コンポーネントの入れ物

エージェント本体・トピック・エンティティ・フロー・環境変数などを1つにまとめる、Dataverse の単位。

WHO

発行元とプレフィックス

誰が作ったコンポーネントかを示す識別子。カスタム発行元を用意し、自組織のプレフィックスを付ける。

WHY

依存関係ごと運べる

エージェント単体ではなく、動作に必要な部品をまとめて移せる。これが手作業の作り直しをなくす鍵。

鉄則エージェントは最初からカスタムソリューションの中で作る。既定のソリューション（Default Solution）はエクスポートできないため、あとから移すことになる。
用語ミニ解説ソリューション：エージェントや関連部品をまとめて入れる「引っ越し用のダンボール箱」。この箱ごと運ぶコンポーネント：箱に入れる部品のこと。エージェント本体、トピック、フローなど1つ1つを指すDataverse：Power Platform のデータの保管庫。ソリューションはこの中に作られる発行元／プレフィックス：部品に付ける「製造元ラベル」。自社の略称（例：contoso）を付けて他社製と区別する
  • 「箱に入れる」比喩で説明すると非エンジニアにも伝わる。
  • 既定ソリューションで作ってしまった場合も、既存コンポーネントとしてカスタムソリューションに追加すればリカバリできる。
OVERVIEW

移管の全体フロー

  • ① 準備（移行元）カスタムソリューションを新規作成し、発行元とプレフィックスを決める
  • ② 梱包（移行元）エージェントを追加し、「必要なオブジェクトを追加」で依存関係を取り込む
  • ③ エクスポート（移行元）すべての変更を公開 → マネージド／アンマネージドを選び zip をダウンロード
  • ④ 受け入れ準備（移行先）Dataverse・リージョン・セキュリティロール・ライセンス／容量を確認
  • ⑤ インポートと事後作業（移行先）接続参照と環境変数を設定 → 認証を再構成 → 公開 → チャネル設定
用語ミニ解説エクスポート／インポート：箱を zip ファイルとして書き出すこと（エクスポート）と、別の環境で取り込むこと（インポート）
  • この5ステップが資料全体の骨格。以降のパートは、この番号に対応している。
SCOPE

何が運ばれ、何が運ばれないのか

ソリューションで運べる
  • エージェント本体とトピック
  • エンティティ（カスタムエンティティ）
  • Power Automate フロー
  • カスタムコネクタ・接続参照の定義
  • 環境変数（定義。値は環境ごと）
  • Dataverse テーブルなどの関連コンポーネント
運ばれない・作り直しが必要
  • トピック／ノードに付けたコメント
  • 会話 ID・ボット ID・環境 ID
  • エージェントのアイコン
  • チャネルの詳細設定（展開済みチャネル含む）
  • ユーザー認証の設定・Direct Line / Web チャネルのセキュリティ
  • Application Insights の設定、共有設定
読み替え方右側のリストが、そのまま移行後にやる作業リストになる。PART 5 で1つずつ対処法を見ていく。
用語ミニ解説依存関係：そのエージェントが動くために必要な、ほかの部品とのつながり接続参照：エージェントが外部サービス（Outlook、SharePoint など）につなぐための「差し込み口」の設定環境変数：環境ごとに変わる値（URL やアドレス）を、あとから差し替えられるようにしておく仕組みチャネル：エージェントを使ってもらう窓口。Teams、自社サイトへの埋め込みなど
  • 右側が「移行後の作業リスト」そのものになる。PART 5 で再掲する。
  • 特に認証設定が引き継がれない点は、事前に伝えておかないと当日に慌てる。
PART 2

移行元環境での準備

ソリューションの作成と、エージェント・依存関係コンポーネントの追加

  • ここから実作業。画面を見せながら進めると理解が早い。
PREREQUISITES

始める前のチェック

  • 権限 — 移行元・移行先の両方で「システムカスタマイザー」以上のセキュリティロールを持っている
  • 環境 — 両環境とも Dataverse データストアがあり、Copilot Studio が利用できる
  • 発行元 — カスタム発行元とプレフィックス（例：contoso）を決めてある
  • 依存関係の把握 — エージェントが使うフロー・カスタムコネクタ・環境変数・テーブルを一覧化してある
  • 公開状態 — エクスポート前に「すべての変更を公開」できる状態になっている
用語ミニ解説セキュリティロール：その人が何をしてよいかを決める権限のセット。「システムカスタマイザー」は設定変更ができるレベルすべての変更を公開：編集した内容を確定させる操作。下書きのままだと箱に入らない
  • 依存関係の洗い出しがいちばん漏れやすい。作成者本人にヒアリングして書き出しておく。
STEP 1 / 移行元

手順①　カスタムソリューションを新規作成する

  • ソリューション画面を開くCopilot Studio のサイドバー「…」→「ソリューション」。エージェント画面の「…」→「エージェントのエクスポート」でも開く
  • 「新しいソリューション」を選択Power Apps のソリューション作成画面が開く
  • 表示名・名前を入力例：Contoso Agent Migration。用途がわかる名前にする
  • 発行元を選択、または新規作成既定ではなく、自組織のカスタム発行元とプレフィックスを指定
  • バージョンを確認して作成初回は 1.0.0.0。作成後、そのソリューションが自動で開く
用語ミニ解説既定のソリューション：何も指定しないと部品が入る「共用の箱」。この箱は外に持ち出せないので必ず自分の箱を作るバージョン：箱に付ける版数。1.0.0.0 のような番号で、更新のたびに増えていく
  • 発行元プレフィックスは後から変えられないので、ここで組織のルールに合わせる。
STEP 2 / 移行元

手順②　エージェントをソリューションに追加する

  • 作成したソリューションを開くソリューション一覧から選択
  • 「既存を追加」を選ぶコマンドバーの「既存を追加」→「エージェント」（Copilot Studio 側では「エージェント」→ 既存のコンポーネントを追加）
  • 対象のエージェントを選択して追加移行したいエージェントにチェックを入れて追加する
  • 一覧に表示されたことを確認ソリューションの「オブジェクト」にエージェントが並べば成功
ワンポイント「優先ソリューションの設定」を今回の箱にしておくと、以降に作るエージェントが自動でこの箱に入り、次回の移管が楽になる。
用語ミニ解説既存を追加：すでに作ってあるものを箱に入れる操作。新規作成ではない点に注意優先ソリューション：これから作るものが自動的に入る「既定の箱」を指定しておく設定
  • 既存エージェントが既定ソリューションにいる場合も、この手順でカスタムソリューションに紐づけられる。
STEP 3 / 移行元 — 最重要

手順③　依存関係コンポーネントを取り込む

  • エージェントの「必要なオブジェクトを追加」を実行エージェント行の「⋮」→「詳細設定」→「必要なオブジェクトを追加」
  • 入ったコンポーネントを目視で確認フロー／接続参照／環境変数／カスタムコネクタ／テーブルが入っているか
  • 足りないものは「既存を追加」で個別に足す自動で拾えない参照もある。洗い出したリストと突き合わせる
  • 各コンポーネントにも同じ操作を行うフローやテーブル側にもさらに依存先がある。連鎖する依存を取りこぼさない
ここが失敗の最多原因インポートや公開でエラーになる原因は、必要な部品が箱に入っていないことがほとんど。
用語ミニ解説必要なオブジェクトを追加：エージェントが動くのに必要な部品を、システムが自動で探して箱に入れてくれる機能ワークフロー：一覧上での Power Automate フローの表示名。同じものを指している
  • ここを丁寧にやるかどうかで、移行後のトラブル量が決まる。時間をかけてよい工程。
TIPS FOR THIS SCENARIO

先行開発フェーズでやっておく「仕込み」

01

最初からソリューション内で作る

あとから箱に入れるより手戻りがない。優先ソリューションを設定しておけば意識せずに済む。

02

環境依存の値は環境変数へ

SharePoint サイトの URL、API のエンドポイント、宛先メールなど、環境で変わる値をトピックに直書きしない。

03

トピック名にピリオドを使わない

トピック名に . が含まれるエージェントはエクスポートできない。命名規則として先に決めておく。

04

肥大化に注意

トピック250件・エンティティ100件を超える規模は標準の手順外の扱いになる。分割やコンポーネント化も検討。

用語ミニ解説トピック：「〇〇と聞かれたらこう答える」という会話のかたまり。エージェントの中身そのものエンティティ：日付や社員番号など、会話から拾いたい情報の種類の定義
  • この4点を先に伝えておくと、移行当日の手戻りがほぼなくなる。
  • 特に②は、移行後に「動かない」の原因になりやすい。
PART 3

エクスポート

手順と、マネージド／アンマネージドの使い分け

  • 操作自体は短い。判断が必要なのはパッケージの種類だけ。
STEP 4 / 移行元

手順④　ソリューションをエクスポートする

  • 対象ソリューションを選び「エクスポート」アンマネージドのカスタムソリューションを選択する
  • 「すべての変更を公開する」を実行公開済みのコンポーネントだけがエクスポートされる。ここは必ず通す
  • （推奨）ソリューションチェッカーを実行パフォーマンスや構成の問題を事前に検出できる
  • バージョン番号を確認自動で加算される。既定値のままでよいが、運用ルールがあればそれに従う
  • パッケージの種類を選んでエクスポートマネージド／アンマネージドを選択。数分でダウンロードフォルダーに zip が保存される
用語ミニ解説ソリューションチェッカー：箱の中身に問題がないか自動点検してくれる機能。実行は任意だが推奨zip：複数のファイルを1つにまとめた圧縮ファイル。これが引っ越しの荷物そのもの
  • 手順②を飛ばすと「直前の変更が入っていない」という事故になる。強調する。
DECISION

マネージド／アンマネージドの使い分け

観点アンマネージドマネージド
位置づけ開発中のソース完成品としての配布パッケージ
移行先での編集自由に編集できる直接編集不可（レイヤーで上書き管理）
再エクスポートできるできない
ソリューション削除時コンポーネントは環境に残るまとめて削除される（きれいに戻せる）
主な用途開発環境どうしの移動、バックアップテスト環境・本番環境への配布
今回のケースの選び方新環境が今後の開発の本拠地になるなら「アンマネージド」。既存環境を開発用に残すなら「マネージド」。迷ったらまずアンマネージドで移す。
用語ミニ解説マネージド：中身を直接いじれない「完成品」として渡す形式。配布・本番向けアンマネージド：中身を自由に編集できる「作りかけ」の形式。開発を続ける環境向けレイヤー：マネージドの上に変更を重ねる仕組み。元の中身は残したまま上書きされる
  • ここは正解が1つではない。お客様の環境戦略（開発をどちらでやるか）を確認してから決める。
PART 4

移行先環境の受け入れ準備

Dataverse・ロール・そしてライセンスと容量の紐づけ

  • 今回いちばん引っかかりやすいパート。時間を取って説明する。
TARGET ENVIRONMENT

新しい環境に必要な条件

  • Dataverse データストアあり — 環境作成時に「Dataverse データストアを追加」を選んでいること。無いと Copilot Studio の環境一覧に出てこない
  • サポート対象リージョン — Copilot Studio が提供されている地域で作成されていること
  • 環境の種類 — 試用版は有効期限切れで中身ごと消える。本格運用するなら「運用環境」で作成する
  • セキュリティロール — 作業者に「システムカスタマイザー」以上、加えて「エージェントの作成者」ロールが割り当てられていること
  • 環境スイッチャーに表示される — Copilot Studio 上部の環境切り替えで新環境を選択できる状態
用語ミニ解説Dataverse データストア：環境を作るときに一緒に用意するデータの保管庫。無いと Copilot Studio が使えないリージョン：そのサービスが動いているデータセンターの地域。日本など対応地域を選ぶ試用版／運用環境：試用版はお試し用で期限が来ると中身ごと消える。本番で使うなら運用環境
  • 「環境一覧に出てこない」問い合わせの原因は、たいていデータベース未作成かリージョン。
LICENSING — 今回の要注意ポイント

ライセンス・容量が未紐づけだと、どこまで進めるか

新環境の状態進められること止まる可能性があること
ライセンス／容量が未割り当て
試用ライセンスのみの場合を含む		ソリューションのインポート、エージェントの編集、テストチャットでの動作確認エージェントの公開、チャネル展開、エンドユーザーへの提供
容量を割り当て済み
前払いクレジット、または従量課金で Azure サブスクリプションを紐づけ		公開・チャネル展開まで含めて通常どおり利用できる—
段取りの提案「インポートまでは進めておき、ライセンス手配が完了してから公開する」と分けて計画する。従量課金の場合は、Power Platform 管理センターで課金ポリシーを作り、対象環境をリンクする作業が別途必要。
※ライセンス要件は変更されることがあるため、実施前に最新のライセンス ガイドで確認すること。
用語ミニ解説容量（クレジット／メッセージ）：エージェントとの会話回数に応じて消費する利用枠。前払いで買うか、使った分だけ払う従量課金（従量制）：Azure サブスクリプションを環境に紐づけ、使った分だけ後から支払う方式Azure サブスクリプション：Microsoft のクラウド利用料を支払うための契約単位。ここに請求がまとまる課金ポリシー：どの環境の料金をどの契約で払うかを決める設定。管理センターで作成する
  • お客様の「まだサブスクリプションと紐づいていない」状況を踏まえたスライド。
  • 作業日をどう分けるか、この場で握ってしまうのがよい。
PART 5

インポートと事後作業

取り込んで終わりではない。動く状態に戻すまでが移管

  • ここからが本番。事後作業の漏れが「動かない」の原因になる。
STEP 5 / 移行先

手順⑤　ソリューションをインポートする

  • 新環境でソリューション画面を開く画面上部で新環境に切り替え、「ソリューションのインポート」を選ぶ
  • zip ファイルを選択「このデバイス」から zip を指定。カスタムコネクタがある場合は先に取り込む（95 MB まで）
  • 詳細設定を確認「含まれるプラグインステップとフローを有効にする」のチェックをどうするか決める
  • 接続参照と環境変数を設定新環境の接続を選択または新規作成し、環境変数には新環境用の値（URL や ID）を入力する
  • インポートを実行失敗したらログをダウンロードして原因を確認
用語ミニ解説プラグインステップとフロー：裏側で自動的に動く処理。チェックを外すと止まった状態で取り込まれるログファイル：処理の記録。失敗した理由が書いてある。XML 形式なので Excel で開くと読みやすい
  • フローを無効のまま取り込み、確認後に有効化する運用も安全でよい。
POST-IMPORT 1

事後作業①　接続参照と環境変数

接続参照

新環境の接続を作り直す

接続そのものは環境に紐づくため引き継がれない。インポート時に設定していない場合は、ソリューション内の接続参照を開いて接続を選択・新規作成する。作成者アカウントで作った接続は、他の利用者に共有されているかも確認する。

環境変数

新環境の値を入れ直す

環境変数は「定義」が移り、「値」は環境ごとに設定する。SharePoint サイト、API エンドポイント、宛先アドレスなどが移行元のままになっていないか、ひとつずつ確認する。

確認のコツソリューション内の「接続参照」「環境変数」を一覧表示し、値が空のものが無いかをチェックすると漏れが出にくい。
用語ミニ解説接続参照：エージェントと外部サービスをつなぐ「差し込み口」。差し込む相手（接続）は環境ごとに作り直す環境変数：URL やアドレスなど、環境で変わる値の置き場所。定義は運ばれるが中身の値は入れ直す
  • ここが未設定だと、動くように見えて特定のトピックだけ失敗する、という分かりにくい壊れ方をする。
POST-IMPORT 2

事後作業②　ソリューションに含まれない設定を戻す

  • ユーザー認証 — 認証方式を設定し直す。Microsoft Entra ID の手動構成を使っている場合は、アプリ登録・クライアント ID・スコープ・リダイレクト URL を新環境向けに再設定する
  • Direct Line / Web チャネルのセキュリティ — シークレットやトークンの設定は引き継がれない
  • 展開済みチャネルの設定 — Teams や Web サイト埋め込みなど、チャネルごとの構成をやり直す
  • Application Insights — 分析連携を使っている場合は接続文字列を再設定
  • 共有設定 — 他の作成者・エンドユーザーへの共有は移行されない
テナントをまたぐ場合同一テナント内なら Entra ID のアプリ登録は再利用できることが多いが、テナントをまたぐ場合はアプリ登録も SharePoint 等のナレッジ参照も作り直しになる。今回は同一テナント内のため影響は限定的。
用語ミニ解説ユーザー認証：エージェントを使う人にサインインしてもらう仕組みMicrosoft Entra ID：旧 Azure AD。社員アカウントを管理する仕組みで、サインインの土台になるDirect Line / Web チャネル：Web サイトなどにエージェントを埋め込むときの接続方式Application Insights：利用状況やエラーを記録・分析する Azure のサービス
  • PART 1 の「運ばれないもの」の再掲。ここでは対処までセットで示す。
POST-IMPORT 3

事後作業③　公開とチャネル設定

  • 中身を確認するトピック、ナレッジ ソース、アクションが揃っているか。ナレッジの参照先が移行元を向いていないか
  • テストチャットで動作確認認証が必要なトピック、フローを呼ぶトピックを重点的に試す
  • エージェントを公開する公開しないと共有もチャネル展開もできない。移行後は必ず公開が必要
  • チャネルを有効化するTeams、Web サイトなどを設定。Teams で全社展開する場合は管理者による承認・展開が別途必要
豆知識エージェントのアイコンは移行されない。設定し直したあと、チャネル上の表示に反映されるまで最大24時間かかることがある。
用語ミニ解説ナレッジ ソース：エージェントが答えを探しに行く参照先。SharePoint サイトや公開 Web サイトなど公開（発行）：編集内容を利用者に見せる状態にする操作。公開しないと誰も使えない
  • アイコンの反映遅延は「壊れた？」と誤解されやすいので先に伝えておく。
PITFALLS

Power Automate フロー・コネクタ連携の落とし穴

01

カスタムコネクタは先に

コネクタが無い状態でソリューションを取り込むと参照が壊れる。同梱するか、先に単独でインポートしておく。

02

フローがオフのまま

「プラグインステップとフローを有効にする」を外して取り込むと、フローは無効のまま。確認後に有効化を忘れない。

03

接続の所有者問題

接続は作成者アカウントに紐づく。担当者が異動・退職すると止まる。運用アカウントで作る、共有しておくなどの設計を。

04

オンプレミス ゲートウェイ

ゲートウェイ接続は共有接続である必要がある。インポート後に接続を作り直し、正しいゲートウェイを指定する。

用語ミニ解説Power Automate フロー：メール送信や承認など、決まった処理を自動で実行する仕組みカスタムコネクタ：標準では用意されていない外部システムにつなぐための、自作の接続部品オンプレミス ゲートウェイ：社内のサーバーやファイルにクラウドから安全につなぐための中継役
  • フロー連携があるエージェントは、移行後の不具合の大半がこの4つのどれか。

SUMMARY

まとめ

3つの要点

先行開発は成立する

ソリューションで梱包しておけば、新環境ができてから安全に引っ越せる。ただし①最初からソリューション内で作る、②環境依存の値は環境変数に逃がす、③公開にはライセンス／容量が要る、の3点を先に押さえること。

いちばん効く準備依存関係の洗い出しと「必要なオブジェクトを追加」。ここが丁寧なら移行はほぼ成功する。
